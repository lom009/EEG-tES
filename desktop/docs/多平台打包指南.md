# Velopack 多平台打包指南

本文面向需要生成安装包、便携包和更新产物的开发者。项目使用 .NET 10 和仓库固定的 Velopack 1.2.0，以 Release、自包含方式发布，目标机器无需预先安装 .NET 运行时。

Windows 自定义目录选择界面的生成方式、两次 `dotnet publish` 与 Velopack 的衔接、运行时体积和远程更新关系，见 [WindowsSetup 实现流程](WindowsSetup实现流程.md)。

## 1. 环境准备

所有命令均从仓库根目录执行，并需要能够还原 NuGet 依赖和 .NET 本地工具。

| 构建主机 | 环境要求 | 支持的目标 RID |
| --- | --- | --- |
| Windows | .NET 10 SDK、PowerShell | `win-x86`、`win-x64`、`win-arm64`、`linux-x64`、`linux-arm64` |
| macOS | .NET 10 SDK、PowerShell 7、Apple Command Line Tools | `osx-x64`、`osx-arm64` |

脚本自动执行 `dotnet tool restore`，使用 `.config/dotnet-tools.json` 固定的 `vpk` 1.2.0，无需单独安装全局版本。Windows/Linux 打包入口必须在 Windows 上运行；macOS 打包入口必须在 macOS 上运行。当前脚本不支持 32 位 `linux-arm`。

## 2. 参数说明

两个打包入口使用相同的参数：

| 参数 | 是否必填 | 说明 |
| --- | --- | --- |
| `Version` | 否 | 显式指定不带 `v/V` 前缀的 SemVer 2.0.0 版本，优先于 Git 标签；省略时从当前 HEAD 的有效标签解析。显式空值或非法版本会报错。 |
| `SourceBaseAddress` | 是 | 写入包内默认配置的更新源基地址；必须为绝对 HTTP/HTTPS 地址，不得包含查询参数或片段。末尾斜杠会自动去除。 |
| `PublishPath` | 否 | 最终产物输出根目录，默认是仓库下的 `TestArtifacts/Publish`；可指定本地目录、UNC 路径或已挂载的共享目录。 |
| `RuntimeIdentifiers` | 否 | 本次构建的 RID；省略时构建当前入口支持的全部目标。支持单个值、数组或逗号分隔值。 |

下文的 `https://updates.example.com` 是示例地址，打包前应替换为实际更新源基地址。即使只分发安装包，现有脚本也要求传入此参数。构建过程将它写入发布副本的 `appsettings.default.json` 中的 `ApplicationUpdate.SourceBaseAddress`。

所有打包调用示例均省略版本参数，要求已安装 Git，且脚本所属仓库当前 HEAD 上存在有效的版本标签。脚本使用 `git tag --points-at HEAD` 读取本地标签，支持轻量和附注标签，不回溯祖先提交，也不自动拉取远程标签。显式传入 `Version` 时不查询 Git。

有效标签必须以 `v` 或 `V` 开头，剩余部分符合 SemVer 2.0.0，例如 `v1.0.0`、`V1.2.3-rc.1+build.5`。只有一个有效标签时自动采用；多个有效标签按名称稳定排序，列出从 1 开始的序号，输入序号选择，输入无效时重新提示。最终版本会去掉首字符 `v/V`，用于本次全部目标。

没有有效标签或 Git 查询失败时，脚本在构建前报错退出，需为 HEAD 创建有效标签或显式指定 `Version`。非交互构建遇到多个有效标签时，必须显式指定 `Version`。

`PublishPath` 是磁盘目录，`SourceBaseAddress` 是客户端访问地址；两者只追加相同的平台和架构路径：

```text
磁盘：{PublishPath}/win/x64/releases.win.json
URL： {SourceBaseAddress}/win/x64/releases.win.json
```

不同架构使用独立目录，不要混放更新包。配置同步规则见[配置文件说明](配置文件说明.md)。

### 更新基地址的作用与请求规则

`SourceBaseAddress` 告诉安装后的应用“去哪里检查和下载更新”，不是安装包输出目录，也不是上传接口。打包时该值写入包内默认配置；应用启动同步配置后，使用它作为更新源。`AutoCheckOnStartup` 控制是否在启动时自动检查，基地址本身不控制是否启用检查。

应用根据当前运行包的 RID 追加平台和架构路径，例如 `win-x64` 追加 `win/x64`，然后由 Velopack 获取对应平台的发布索引。应用只检查当前运行目标的更新目录，不会逐一请求所有平台。

```text
更新目录：{SourceBaseAddress}/{platform}/{arch}
检查更新：{SourceBaseAddress}/{platform}/{arch}/releases.{channel}.json
下载更新：{SourceBaseAddress}/{platform}/{arch}/{索引中选定的更新包文件名}
```

其中 Windows、Linux、macOS 的 platform/channel 分别是 `win`、`linux`、`osx`。检查索引用于判断是否有更高版本；实际执行更新下载时，再请求选定的完整包或增量包，而不是下载安装用的 Setup/MSI。下表列出索引资源地址，Velopack 实际请求可能附加查询参数。

| 场景 | `SourceBaseAddress` | 运行包 RID | 检查更新的索引地址 |
| --- | --- | --- | --- |
| 本机服务 | `http://127.0.0.1:8080` | `win-x64` | `http://127.0.0.1:8080/win/x64/releases.win.json` |
| 局域网服务 | `http://192.168.1.10:8080` | `win-x86` | `http://192.168.1.10:8080/win/x86/releases.win.json` |
| HTTPS 域名 | `https://updates.example.com` | `linux-arm64` | `https://updates.example.com/linux/arm64/releases.linux.json` |
| 域名下的应用子目录 | `https://downloads.example.com/eggtcs` | `osx-arm64` | `https://downloads.example.com/eggtcs/osx/arm64/releases.osx.json` |
| 基地址带末尾斜杠 | `https://downloads.example.com/eggtcs/` | `win-arm64` | `https://downloads.example.com/eggtcs/win/arm64/releases.win.json` |

`127.0.0.1` 指的是运行应用的那台机器。分发到其他电脑时，应填写那些电脑能够访问的局域网地址或域名。示例中的地址仅用于说明，不代表已有可用的更新服务。

基地址可以带应用子目录，且该子目录会保留。不要将 `win/x64` 等目标后缀或 `releases.win.json` 填入基地址；应用还会自动追加目标路径。例如，误填 `https://updates.example.com/win/x64` 后，Windows x64 会请求 `https://updates.example.com/win/x64/win/x64/releases.win.json`。

### 发布目录与请求地址的完整示例

假设在 Windows 上运行：

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\Build-Publish-WindowsLinuxVelopack.ps1 `
  -SourceBaseAddress "https://downloads.example.com/eggtcs" `
  -PublishPath "D:\ReleaseFiles" `
  -RuntimeIdentifiers win-x64
```

最终索引和客户端请求的对应关系为：

```text
本地索引：D:\ReleaseFiles\win\x64\releases.win.json
请求索引：https://downloads.example.com/eggtcs/win/x64/releases.win.json

本地包：  D:\ReleaseFiles\win\x64\<更新包文件名>.nupkg
请求包：  https://downloads.example.com/eggtcs/win/x64/<更新包文件名>.nupkg
```

这里的 `<更新包文件名>` 必须以实际发布索引中的文件名为准。HTTP 服务需要将 `https://downloads.example.com/eggtcs/` 对应到 `D:\ReleaseFiles\` 的内容；磁盘目录下不需要再增加 `eggtcs` 层。修改 `PublishPath` 只改变文件输出位置，修改 `SourceBaseAddress` 才会改变包内配置的更新访问地址。

脚本负责生成和复制产物，不部署 HTTP 服务，也不会将文件通过 HTTP 上传到基地址。只有发布索引及其引用的更新包可通过上述地址访问时，客户端才可以完成检查和下载。

## 3. Windows/Linux 打包

在 Windows 仓库根目录执行。默认构建全部五个目标：

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\Build-Publish-WindowsLinuxVelopack.ps1 `
  -SourceBaseAddress "https://updates.example.com" `
  -PublishPath ".\TestArtifacts\Publish"
```

只构建 Windows x64：

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\Build-Publish-WindowsLinuxVelopack.ps1 `
  -SourceBaseAddress "https://updates.example.com" `
  -RuntimeIdentifiers win-x64
```

只构建 Windows x64 和 Linux x64：

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\Build-Publish-WindowsLinuxVelopack.ps1 `
  -SourceBaseAddress "https://updates.example.com" `
  -RuntimeIdentifiers "win-x64,linux-x64"
```

这些命令是不同目标选择方式的示例，不应在同一 Releases 历史目录中用同一版本反复执行。需要再次打包时递增版本并更新 HEAD 上的对应标签，或显式指定更高的 `Version`。

## 4. macOS 打包

在 macOS 仓库根目录执行。默认构建两个目标：

```powershell
pwsh ./scripts/Build-Publish-MacOSVelopack.ps1 `
  -SourceBaseAddress "https://updates.example.com" `
  -PublishPath "./TestArtifacts/Publish"
```

单目标和显式多目标示例：

```powershell
# 只构建 Apple Silicon
pwsh ./scripts/Build-Publish-MacOSVelopack.ps1 `
  -SourceBaseAddress "https://updates.example.com" `
  -RuntimeIdentifiers osx-arm64

# 显式选择两个架构
pwsh ./scripts/Build-Publish-MacOSVelopack.ps1 `
  -SourceBaseAddress "https://updates.example.com" `
  -RuntimeIdentifiers "osx-x64,osx-arm64"
```

如需输出到已挂载的共享目录，可指定 `-PublishPath "/Volumes/update-server/releases"`。当前脚本没有配置签名和公证，生成的 macOS 包用于受控测试；正式分发前需另行配置签名和公证。

## 5. 输出产物

脚本先完成本次所选目标的自包含发布和 Velopack 打包，所有目标打包成功后，再逐个将产物发布到 `PublishPath`。发布阶段并非事务：中途失败时，前面目标的产物可能已经写入。

### 构建目录与最终输出目录

| 目录 | 用途 |
| --- | --- |
| `TestArtifacts/Velopack/<RID>/publish/<Version>` | `dotnet publish` 生成的原始自包含应用文件，尚不是安装包。 |
| `TestArtifacts/Velopack/<RID>/Releases` | Velopack 打包产物及版本历史，供后续发布和增量包生成使用。 |
| `TestArtifacts/Velopack/<RID>/setup/<Version>` | Windows 安装目录选择引导器的构建输出。 |
| `<PublishPath>/<platform>/<arch>` | 最终分发目录，包含安装/便携产物、更新包与发布索引。 |

默认最终目录和索引如下，仅生成本次选择的目标：

| RID | 默认输出目录 | 发布索引 |
| --- | --- | --- |
| `win-x86` | `TestArtifacts/Publish/win/x86` | `releases.win.json` |
| `win-x64` | `TestArtifacts/Publish/win/x64` | `releases.win.json` |
| `win-arm64` | `TestArtifacts/Publish/win/arm64` | `releases.win.json` |
| `linux-x64` | `TestArtifacts/Publish/linux/x64` | `releases.linux.json` |
| `linux-arm64` | `TestArtifacts/Publish/linux/arm64` | `releases.linux.json` |
| `osx-x64` | `TestArtifacts/Publish/osx/x64` | `releases.osx.json` |
| `osx-arm64` | `TestArtifacts/Publish/osx/arm64` | `releases.osx.json` |

### 各类产物用途

- Windows：`*-Setup.exe` 为安装入口，MSI 用于 Windows Installer 安装，Portable 为便携分发包。
- Linux：AppImage 为应用分发和启动入口，没有安装目录选择向导。
- macOS：`.pkg` 为安装入口。
- 完整更新包及可生成的增量更新包：供更新客户端使用；首次打包不要预期一定有增量包。
- `releases.<channel>.json`：更新产物索引，平台 channel 为 `win`、`linux` 或 `osx`，应与对应目录中的包一起保留。

Windows 打包脚本将原生 Velopack Setup 嵌入项目提供的图形引导器，仍以 `*-Setup.exe` 输出。运行时可输入路径或点击“浏览”选择安装目录，再通过 Velopack 的 `--installto` 完成安装。

MSI 的 `--instLocation Either` 允许选择当前用户或所有用户安装，不提供任意目录浏览页；静默指定路径可使用 `VELOPACK_INSTALLDIR` 属性。已经安装同一 `packId` 的用户如需迁移安装位置，应先卸载旧版本再安装，覆盖安装不会搬迁现有目录。

构建结束后，检查所选 RID 对应目录的分发文件和发布索引。脚本会验证本地发布索引存在，并输出对应 URL；该输出不代表远端地址已经可访问。普通 `dotnet build` 或 `dotnet publish` 目录不能替代 Velopack 安装产物。

## 6. 版本管理

标签去掉 `v/V` 前缀后，以及显式传入的版本参数，均严格校验 SemVer 2.0.0：必须包含主、次、修订版本，可附加预发布版本和构建元数据。主、次、修订及纯数字预发布标识不允许前导零；标识段不能为空。例如 `v01.0.0`、`v1.0.0-01` 和 `v1.0.0-alpha..1` 均不是有效标签。

使用递增的版本号，例如：

```text
1.0.0-alpha.1 < 1.0.0-alpha.2 < 1.0.0-beta.1 < 1.0.0-rc.1 < 1.0.0 < 1.0.1
```

同一主、次、修订版本下，正式版高于预发布版；数字预发布段按数值比较，例如 `alpha.10` 高于 `alpha.2`。构建元数据不提高更新优先级，不能依靠改变 `+build` 后缀触发升级。

不要在同一个 RID 的 Releases 历史目录重复打包相同版本，也不要覆盖已经分发的版本。保留 Releases 历史以支持后续打包；重新构建时使用更高的 `Version`。如果多目标构建中途失败，部分目标可能已经生成该版本的包，再次运行前也应检查历史并递增版本。

## 7. 常见问题

| 问题 | 处理方式 |
| --- | --- |
| HEAD 没有有效版本标签 | 为当前 HEAD 创建以 `v/V` 开头的 SemVer 标签，或显式传入 `Version`；祖先提交的标签不会被采用。 |
| Git 不可用或标签查询失败 | 检查 Git 安装及仓库信息，或显式传入 `Version` 跳过标签解析。 |
| 非交互构建无法选择多个标签 | 显式传入 `Version`，避免交互选择。 |
| 本地工具或 NuGet 还原失败 | 检查 .NET 10 SDK、网络及 NuGet 源，确认可在仓库根目录执行 `dotnet tool restore`。 |
| 主机平台或 RID 不受支持 | 按入口选择目标：Windows 入口接受五个 Windows/Linux RID，macOS 入口接受两个 macOS RID。 |
| 更新源参数被拒绝 | 使用无查询参数和片段的绝对 HTTP/HTTPS 地址，不要传入磁盘路径。 |
| 相同版本打包失败 | 检查对应 RID 的 Releases 历史，递增版本号后重新打包。 |
| 找不到最终安装包 | 检查脚本是否全部执行成功，以及 `PublishPath` 下对应平台/架构目录；不要只查看原始 publish 目录。 |
| macOS 包缺少分发签名 | 当前脚本未配置签名和公证，正式分发需补齐相关流程。 |

默认构建产物位于 Git 忽略的 `TestArtifacts`。自定义 `PublishPath` 时由调用方管理输出目录。业务数据目录 `%LocalAppData%\EGGtCSPlatform` 不属于构建输出或清理目标。
